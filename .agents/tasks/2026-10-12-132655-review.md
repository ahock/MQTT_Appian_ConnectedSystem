# AppMarket compliance: package rename to de.hock.mqtt, 26.9 manifest, source-bearing plug-in jar

The change clears the three AppMarket rejection causes this repo carried: the plug-in lived under the reserved `com.appian.*` namespace, the shipped jar contained no source code, and the manifest declared Appian itself as vendor against an 18.4 floor. All 33 main sources plus the single test source moved to `de/hock/mqtt`, the pom groupId became `de.hock`, `appian-plugin.xml` was rewritten for 26.9 with `key="de.hock.mqtt"` and `vendor name="Hock"`, and the maven-assembly descriptor (renamed `src/assembly/plugin-assembly.xml` to end the filename collision with the real manifest) now ships `.java` sources root-mirrored beside their classes, moves Paho from root `lib/` to `META-INF/lib/`, and adds `THIRD-PARTY-NOTICES.md`. `default-jar` is bound to phase `none` so exactly one jar lands in `target/`. I rebuilt from clean and re-ran every checklist item rather than trusting the recorded findings.

Watch for: the vendor URL `https://hock.de` is still a planning assumption, not a user-supplied value (**confirmed** — it sits on line 28 of the manifest; DNS resolves to parking-range addresses, so ownership is unverified). The plug-in key change forces existing installations to be removed and connected-system objects re-pointed (**confirmed** from the key edit). `META-INF/lib` nested-jar resolution and the absence of connected-system logo assets can only be settled on a real 26.9 instance or by the reviewer (**possible**, undecidable from this repo).

**Verdict**: APPROVED

## High-level view

The rename is complete and surgical. 33 sources under `src/main/java/de/hock/mqtt`, 1 under `src/test/java/de/hock/mqtt`, no `com` tree anywhere in `src`, groupId `de.hock`, and zero `com.appian.mqtt` / `com/appian/mqtt` strings across `src pom.xml docs info.md .kiro THIRD-PARTY-NOTICES.md`. The anchored sed left the SDK intact: 55 `com.appian.connectedsystems` references survive. No `com.appiancorp.*` import ever existed here, so that half of the "SDK untouched" requirement is vacuously met rather than demonstrated.

The manifest carries every required 26.9 value, and the one thing that would silently break registration was not broken: all three `key=`/`name=` attributes still equal the `@TemplateId` names, and the six `resources_en_US.properties` entries still key off the simple class names. Request policies are unchanged (Publish WRITE, Subscribe READ).

Packaging, the part that actually answers the rejection, holds up under inspection: 33 `.java` entries all under `de/hock/mqtt/` and path-identical to `src/main/java`, manifest and bundle at the archive root, Paho as the single `META-INF/lib/` nested jar, no test code, no `META-INF/maven`, no `connected-systems-core`. `maven-source-plugin` was correctly not used — a sibling `-sources.jar` would not have satisfied "source within the executable".

One checklist number in the plan is wrong, not the build. Item 18(d) expects 48 `.class` entries; the jar has 38. A sorted diff of the jar's class entries against `target/classes` is identical, so the assembly drops nothing — 48 is a stale figure carried from the earlier audit and should be corrected in the plan so the next pass does not read it as a packaging gap.

Scope was respected: SDK still `connected-systems-core:1.9.1`, no `Simple*` migration, no `connected-systems-client` dependency, no logging framework invented, no new tests, and `docs/mqtt-plugin-guide.md` edited only at the two named spots. Three open items are carried deliberately rather than silently dropped — the SDK compatibility-table divergence (DD-2), the missing logo artwork, and the vendor URL.

### The appiancorp half of the SDK-integrity gate is empty

Plan item 20 expects `grep -rn 'com\.appian\.connectedsystems\|com\.appiancorp' src/main/java | wc -l` to be `>0` as proof the SDK imports were left alone. It passes on the `connectedsystems` half only; `com.appiancorp` has a count of zero in `src/main/java` and, as far as this working tree shows, never appeared in Java sources at all. The only `com.appiancorp` token anywhere in `src` is an explanatory word in the manifest header comment. If that combined grep is ever used as the sole SDK-integrity gate, half of it proves nothing either way.

### Registration contract: key/name/@TemplateId/i18n

A cosmetic cleanup anywhere in this triangle would deploy silently and never register a template:

```
appian-plugin.xml                     @TemplateId(name=...)              resources_en_US.properties
  key/name=MqttConnectedSystemTemplate  MqttConnectedSystemTemplate      MqttConnectedSystemTemplate.name/.description
  key/name=MqttPublishIntegration       MqttPublishIntegration           MqttPublishIntegration.name/.description
  key/name=MqttSubscribeIntegration     MqttSubscribeIntegration         MqttSubscribeIntegration.name/.description
            class= → de.hock.mqtt.{template,integration}.*
```

Only the `class=` attributes moved to the new FQNs; the bundle was confirmed rather than edited, since the rename never touched the simple class names those keys derive from.

Paho stays bundled rather than shaded, which matters more now than before: rewriting its package names inside a jar that also ships its own sources would make the shipped sources and classes disagree.

### Policy sweep and the silent-failure posture

Re-run, not taken on trust: no `System.out`/`System.err`/`printStackTrace`/`java.util.logging`/`System.setProperty`/`java.io.File`/`java.nio.file` in `src/main/java`; no SNAPSHOT in the pom; no Log4j, SLF4J, or Logback anywhere.

That last one deserves disclosure now that sources ship inside the jar: there is no logging framework at all, and failure paths are silent by construction. `resolveDocumentBytes` swallows `IOException` and returns `null` so resolution falls through to the runtime layer, and a reviewer reading the source will see a catch block that leaves no trace of what failed. Not inventing a logging stack was the correct call for a compliance fix; this is a disclosure item, not a change request.

The `Closeable` fix calls `doc.getInputStream()` exactly once into a local, so the null check cannot open and leak a second stream, and the null-early-return, empty-array-to-null, and `IOException → null` behaviors are preserved. The two `ByteArrayInputStream` sites were deliberately left unwrapped: try-with-resources at `CertificateLoader.parseCertificate` would force a `catch (IOException)` arm that can never fire. That step was explicitly optional and the policy targets handle-holding resources.

### Test coverage

Unchanged and thin, deliberately: one file, three smoke assertions (base package name, `appian-plugin.xml` on the classpath, `resources_en_US.properties` on the classpath), all passing after the rename. The base-package assertion and its message both moved to `de.hock.mqtt`, so the test was re-pointed rather than weakened to pass.

Not tested: publish and subscribe against a broker, TLS/mutual-auth certificate paths, LWT, reconnection, validation, diagnostics redaction. `net.jqwik:jqwik:1.8.4`, `io.moquette:moquette-broker:0.17`, the surefire `**/*Properties.java` include, and the whole failsafe `**/*IT.java` execution are configured against files that do not exist — dead config, left alone as out of scope. With sources now inside the submitted jar, a reviewer will read code that has no behavioral coverage behind it; the guide says so in its "Current test coverage (important)" section.

### Documentation

Dropping the guide's warning against deploying the plain jar is correct only because the build ended on DD-6's primary phase-`none` path, not the documented fallback — `ls target/*.jar` returns exactly one file, so the warning would have described a jar that no longer exists. The header's stale `18.4.0.0` floor was corrected to `26.9.0.0` and a plug-in key line added, keeping the guide consistent with the rewritten manifest. `info.md` went from 0 bytes to a ~25-line AppMarket-facing summary.
